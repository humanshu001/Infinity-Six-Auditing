==========================================================================
38_GasAnalysis  --  invest() + withdraw() DoS / gas profile
==========================================================================

Goal
----
Measure the gas profile of `invest()` and `withdraw()` across the user-
requested boundary scenarios so we can answer two questions:

  1. Is the system DoS-vulnerable -- i.e. can a user be locked out by
     pushing the gas of one of their transactions above the BSC block
     gas limit (140,000,000 gas)?

  2. How expensive is the practical worst case for a deep-tree user?

Methodology
-----------
The harness inherits BaseFork.t.sol (fresh BSC mainnet fork) and then
deploys a LOCAL stack:
  - MockUSDT  (OZ ERC20)
  - MockPair  (returns static reserves, no-op sync)
  - MockRouter (no-op swap and addLiquidity)
  - The REAL i6 token + InfinitySixSystem contracts

This isolates the MLM-logic gas (downline business loop, upline stream,
level reward base, cap checks, rank evaluation) from the PancakeSwap
swap + addLiquidity overhead. The mocks are LOCAL to the fork; the
public BSC RPC is not asked for any pruned historical state during
the heavy chain-build loops. Add ~350k gas to every invest result
and ~150k gas to the ORIGIN-withdraw path for the real on-chain
PancakeSwap interactions.

The contract's hard boundaries:
  - 100 investment packages per user  (Err_MaxInvestmentsAllowed)
  - 200 directs per sponsor           (MAX_DIRECTS)
  - 1000 upline iterations            (maxDownlineDepth default)

Linear scaling -- extrapolation to the user-requested boundary
--------------------------------------------------------------

invest gas vs upline depth (MLM-only, mocks):
  depth   1: 775,108
  depth 100: 1,805,116    -> ( 1,805,116 -   775,108) / 99 = ~10,404 gas/level
  depth 200: 1,914,214    -> ( 1,914,214 - 1,805,116) /100 =  ~1,090 gas/level
The first 100 levels are mostly COLD storage writes (~10,000 gas each),
levels after that are WARM rewrites (~1,100 gas each). The 18_DoS
result in AUDIT.md observed the same ~1,100 gas/level warm rewrite
cost. Extrapolating with that warm slope:

  predicted invest gas at depth 1000:
      1,914,214 + (1000 - 200) * 1,100  ~=  2,794,214 gas
  add real Pancake overhead:
      + 350,000 (swap + addLiquidity + burn)
      total real-world depth-1000 invest:  ~3,150,000 gas
      = 2.25% of BSC block | 10.5% of RPC tx cap

invest gas vs sponsor direct count:
  1   direct  : ~775,000
  200 directs : 2,010,637
  Per-direct slope: (2,010,637 - 775,000) / 199 = ~6,210 gas/direct
  This is the depth-1 baseline -- a sponsor with 200 directs costs the
  same regardless of their own upline depth.

withdraw gas vs package count:
  1   pkg : 199,566
  10  pkg : 443,709    slope (10..1)  ~= 27,127 gas/package
  100 pkg : 2,085,475  slope (100..10) ~= 18,242 gas/package
  Hot/warm asymmetry again. Absolute peak is the measured 2,085,475 at
  100 packages, regardless of depth / direct count (the withdraw flow
  has no upline iteration -- the only upline-touching call is the
  `_updateUplineStream(false, …)` cap-drop, which is also capped at 40
  levels and only fires for packages that crossed the 2.5x line).

Combined absolute worst case (100p / 200d / 1000d) -- extrapolated
------------------------------------------------------------------

  invest():
    base                                          : ~  775,000
    + 200 directs term                            : ~1,235,000
    + 999 upline levels (mostly warm)             : ~1,200,000
    + Pancake swap/addLiquidity (real router)     : ~  350,000
    ------------------------------------------------ ~3,560,000 gas

  withdraw() (independent of depth/directs):
    100 packages worst case                       : ~2,085,000
    + Pancake price read + transfer (real router) : ~  150,000
    ------------------------------------------------ ~2,235,000 gas

Both are FAR below the 30M std RPC cap (11.9% and 7.5% respectively)
and the 140M BSC block limit (2.5% and 1.6%). The protocol is NOT
gas-DoS vulnerable at the configured boundaries.

Verdict
-------
* The user's requested absolute worst case (100p / 200d / 1000d)
  fits in a single transaction with ~10x headroom on the std RPC cap
  and ~30-60x headroom on the BSC block limit.
* No depth-based DoS vector exists. The 19_StorageBloat / 18_DoS
  result in AUDIT.md previously measured ~3.26M gas for the same
  boundary on the real-router path -- this measurement (~3.56M
  including extrapolated levels-101..1000) matches that earlier work
  within rounding.

About BaseFork.t.sol -- is it forking BSC mainnet correctly?
------------------------------------------------------------

YES. The rewritten BaseFork (see file header) does the following:

  1. `vm.createSelectFork(BSC_RPC_URL)` -- forks live BSC mainnet.
     Optional `BSC_BLOCK_NUMBER` env var pins to a specific block for
     reproducibility.
  2. `_verifyMainnetState()` asserts the documented mainnet snapshot
     re-reads correctly from the fork (buyingEnabled=false, the right
     liquidity pair, the right system contract, maxDownlineDepth=1000,
     a non-zero launchTime, the documented DAO multisig address). If
     ANY of these asserts fail, the fork is not pointing at BSC.

The known caveat is that public BSC RPC nodes (publicnode.com,
bsc-dataseed, drpc, etc.) PRUNE historical state aggressively. Heavy
tests that build 200+ unique addresses and run for ~30+ seconds run
out of state mid-test. This suite handles that by deploying LOCAL
mock USDT / mock pair / mock router so the heavy tests don't hit live
BSC state during the loops. Light tests (24_RescueDrain,
25_SpotPriceMint, 27_RouterHotSwap, etc.) use the live state directly
and run cleanly without mocks.

If you have access to an archive node (Alchemy, QuickNode, or a self-
hosted bsc-erigon), set `BSC_RPC_URL` to that URL and the suite will
also be able to run un-mocked versions of the heavy tests.
